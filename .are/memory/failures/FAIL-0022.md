# FAIL-0022 — `(require 'aidermacs)` in an ERT test made vterm ask "Compile vterm-module? (y or n)" on stdin; the suite hung at test 83 of 109 until killed

| | |
|---|---|
| **Date found** | 2026-09-14 |
| **Severity** | MEDIUM |
| **Category** | verification-gap, self-inflicted |
| **Area** | `tests/run-tests.el` (`rata-test-llm-tools-start-on-the-default-provider`), `just/test.just` `test-ert` |
| **Origin** | introduced the same session, while adding tests for D-022 |
| **Status** | FIXED |

## Symptoms

`just test-ert` stopped producing output after

```
   passed   82/109  rata-test-llm-provider-problems-name-the-entry (0.000313 sec)
Vterm needs `vterm-module' to work.  Compile it now? (y or n)
```

and sat there for over seven minutes, past the tool's 400 s timeout, until the Emacs
process was killed by hand. `/proc/<pid>/wchan` was `unix_stream_data_wait` and fd 0 was a
socket: a blocking read of standard input. No test failed; no summary line was printed.

## Mechanism

The new test wanted to assert that the use-package `:custom` value for
`aidermacs-default-model` had been applied, and did `(require 'aidermacs nil t)` to make
the `defcustom` run (the value is void until then — Custom holds it under the use-package
theme and applies it at declaration, the same way the ACP adapter pins work).

`aidermacs.el` requires `aidermacs-backends`, which unconditionally requires
`aidermacs-backend-vterm` (`aidermacs-backends.el:24`), which does `(require 'vterm nil
'noerror)` at load (`aidermacs-backend-vterm.el:24`). vterm's own load-time code finds no
compiled `vterm-module` on this checkout and calls `y-or-n-p`. In batch, `y-or-n-p`
reads its answer with `read-string`, i.e. `read-from-minibuffer` on standard input.
Under the `just` recipe stdin was whatever the caller had — here a socket, so the read
blocked forever; on a TTY it would have waited for a keypress; only with `/dev/null`
would it have errored (`Error reading from stdin`) and failed the suite visibly.

FAIL-0021 had put a fence around the one class of blocking read that had already bitten
(a passphrase prompt reached through the network). The general form — *any* minibuffer
read in batch is a hang or an abort — had no fence.

## Remediation

- The test requires `aidermacs-models`, which is where the `defcustom` lives, and
  which requires only `json` and `url`. That is enough to make Custom apply the value.
- **Harness-wide fence**: `tests/run-tests.el` overrides `read-from-minibuffer`,
  `read-string` **and** `yes-or-no-p` to signal `rata-test: something prompted on stdin
  (<prompt>); stub it in the test`. One entry was not enough: the first version advised
  only `read-from-minibuffer`, and a probe of the five prompt kinds showed it caught
  `completing-read` alone — `read-string` and `yes-or-no-p` are C primitives that reach the
  minibuffer reader inside C, where Lisp advice is invisible, and `y-or-n-p` goes through
  `read-string` in batch. The probe was rerun after each addition until all five signalled;
  the second run, made without `< /dev/null`, itself hung on `yes-or-no-p` and had to be
  killed, which is the failure this record is about. A test that needs an answer shadows
  the reader with `cl-letf`, as the network fence's tests do.
- **Recipe**: `test-ert` now runs with `< /dev/null`, so a C-level read the advice cannot
  intercept errors out instead of waiting.

## What would have caught it sooner

The fence and the redirect above. Also: a `require` in a test is not free — read the
package's top-level forms (and those of what *it* requires) before loading it in batch.
Requiring the sub-file that owns the variable is usually enough and loads less.

Related: FAIL-0021 / L-049 (the prose rule needs a fence in the harness), FAIL-0016 (why
the test wanted to load the package at all).
