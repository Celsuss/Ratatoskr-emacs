# FAIL-0023 — `just compile` sits idle for minutes on `lisp/init-dashboard.el` after "Importing package-keyring.gpg..."

| | |
|---|---|
| **Date found** | 2026-09-30 |
| **Severity** | LOW |
| **Category** | verification-gap, performance |
| **Area** | `just/emacs.just` `compile`, `lisp/init-dashboard.el` |
| **Origin** | pre-existing; found while running `are-verify` for plans/ai-control-center.md |
| **Status** | FIXED 2026-10-06 — `use-package-ensure-function` is `ignore` in the compile recipe |

## Symptoms

`just are-verify relevant` took 11 min wall time for 90 s of CPU, and `full` 8 min for 91 s
(the INDEX expects ~2 and ~3 min). During the `compile` step the per-file Emacs for
`lisp/init-dashboard.el` stayed alive over a minute with zero CPU: `/proc/<pid>/wchan`
`wait_woken`, fd 0 a socket. Its output ends with `Importing package-keyring.gpg...` /
`...done`, printed by package.el, which this config disables at startup (`early-init.el`).
It completes eventually and the step reports PASS, so no gate fails — only slow.

## What is known / not known

- Known: only `compile` (bare `--batch`, no `early-init.el`) shows it; the ERT and startup steps
  do not. The compile recipe, unlike `test-ert` (FAIL-0022), does not redirect stdin from
  `/dev/null`.
- Not known: what in compiling `init-dashboard.el` activates package.el, and whether the wait is
  gpg/gpg-agent or a stdin read. Next step: `strace -f -e trace=read,connect` on that one
  compile, then decide between `< /dev/null` in the recipe and fixing the dashboard's
  compile-time dependency.

## Mechanism (established 2026-10-06)

`use-package` with `:ensure t` installs **at byte-compile time**. The compile recipe runs
bare `--batch`, so `early-init.el` never disables package.el and `use-package-ensure-function`
is package.el's: for every not-installed package it imports the keyring (the message above),
refreshes the archive contents from `elpa.gnu.org` / MELPA, and installs into `./elpa/`. The
idle wait is a network read, not gpg and not stdin. It was slow on 2026-09-30 and became a
hang on 2026-10-06, when `elpa.gnu.org` was unreachable (`curl` timed out at 15 s with no
status): the `compile` step sat on `lisp/init-dev.el` for six minutes and on
`lisp/init-elfeed.el` for five before it was killed, with `Contacting host: elpa.gnu.org:443`
as the last line. A side effect nobody had noticed: `./elpa/` (gitignored) held real
package.el installs — `elfeed-4.1.1`, `casual`, `compat`, `csv-mode`, ... — that nothing loads.
`init-dashboard.el` was simply the first module whose packages were not already there.

Evidence for the fix: the same compile of `lisp/init-elfeed.el` with
`--eval "(setq use-package-ensure-function #'ignore)"` finished in 0.5 s with elpa still
unreachable, and the whole `just compile` in 21 s. Compiling checks syntax and macro
expansion; it has no business installing anything, and with `ignore` the `:ensure` keyword
still expands, so nothing the step proves is lost. stdin is now `/dev/null` as well, the
FAIL-0022 rule. The three `Failed to parse package ...: :ensure wants an optional package
name` lines that remain are package.el's use-package rejecting elpaca recipe forms
(`:ensure (:host ...)`) at parse time; they predate this and do not wait on anything.
