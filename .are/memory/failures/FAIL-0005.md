# FAIL-0005 — the pre-commit gate exists but is not installed

| | |
|---|---|
| **Date found** | 2026-08-19 (ARE bootstrap) |
| **Severity** | MEDIUM |
| **Category** | verification-gap, configuration |
| **Area** | `.githooks/pre-commit`, git config |
| **Origin** | pre-existing |
| **Status** | FIXED in this checkout — CI added 2026-08-24 (`.github/workflows/ci.yml`); `core.hooksPath` set 2026-08-25. Latent in any fresh clone; see Root cause |

## Symptoms

```
$ git config --get core.hooksPath
(empty)
```

`.githooks/pre-commit` exists and runs the test suite. `just install-hooks` exists and sets
`core.hooksPath`. Neither has been run in this checkout, so git is still using
`.git/hooks/`, which contains only the stock samples.

**There is no CI in this repository** — no `.github/`, no `.gitlab-ci.yml`, verified absent.
The pre-commit hook is therefore the *only* automated gate that could exist, and it is off.
Every commit in this repo has been made without any check running.

> **Update 2026-08-24:** CI now exists — `.github/workflows/ci.yml` runs the fast tier
> (`lint`, `compile`, `test-claude-loop`, `are-audit`) and the heavy tier (`test-ert`,
> `batch`) on every PR to `master` and on push to `master`, composing the same `just`
> targets as `are-verify full`. This closes the "no CI" half: master is now gated
> independently of whether any operator installed the local hook. The remaining half is
> that `core.hooksPath` is still unset in this checkout, so *pre*-commit feedback is still
> off — CI catches a bad change at PR time, not at commit time. To make CI *block* merges,
> the two jobs must be marked as required status checks in the repo's branch protection
> (a GitHub setting, not committable).

> **Update 2026-08-25:** the remaining half is now closed here. `core.hooksPath` is
> `.githooks` in this checkout and the hook is not merely configured but *proven*: it ran
> `just are-verify full` against merge commit `255d4be` and reported PASS across lint,
> compile, batch-startup, ERT (42/42), claude-loop e2e and are-audit. Cost is real — the
> commit took roughly three minutes, and two earlier attempts were killed by a 90 s and a
> 120 s timeout before anyone realised the hook was what was running.
>
> This does **not** retire the record. The root cause below is per-clone config, which no
> commit can change, so every new clone reopens the same gap. `are-audit`'s `hooks-installed`
> check stays a warning for exactly that reason.

## Root cause

`core.hooksPath` is per-clone local configuration; it is not carried by a clone and cannot
be committed. So a repo that ships hooks in `.githooks/` **always** starts with them
disabled, in every checkout, forever, until someone runs the install step by hand. Both
checkouts on this machine are in that state.

Repos with CI do not notice, because CI catches what the hook would have. This one has no CI.

## Why it escaped detection

Nothing reports the gate's own status. `just test` passing tells you the tests are fine; it
says nothing about whether anything runs them when it matters. The `README.org` command
table lists `just install-hooks` as "one-time setup", which reads as done rather than
pending.

## Impact

Bounded but real: the operator can commit a config that fails `just test`. Given that this
repository *is* the editor, a bad commit that reaches the other checkout or another machine
costs a broken editor at the next start. `rata-load-module` limits the damage to one module
rather than total failure.

## Fix

**Applied 2026-08-25, on operator instruction.** The ~3-minutes-per-commit cost was the
reason this sat unapplied — it is a workflow decision, not a defect fix, so it was the
operator's to make. They made it. In any other checkout it remains unapplied and the
recommendation below stands:

```sh
just install-hooks
```

The hook now runs `just are-verify full` (see [FAIL-0004](FAIL-0004.md)), so installing it
gates lint, compile, startup, ERT, the claude-loop e2e suite and the ARE audit.

If ~3 minutes per commit is too slow to accept, the useful compromise is a hook that runs
`just are-verify fast` (~4 s) and leaves `full` to be run deliberately before pushing.

## Regression protection

`scripts/are-audit.sh` check `hooks-installed`: warns (does not fail) when
`core.hooksPath` is not `.githooks`. A warning rather than a failure on purpose — a
checkout that has not been set up is not broken, and failing the audit would make the audit
unusable on a fresh clone. The session-start hook surfaces the warning at the top of every
session, which is where it will actually get acted on.

`scripts/are-audit.sh` check `hooks-docs-current` (added 2026-08-25): **fails** when the
gate is installed but `AGENTS.md` or `.are/INDEX.md` still says it is not. Those two are
read at the start of every session, so a stale line there is acted on; failure records and
knowledge pages are exempt because they carry historical present tense on purpose. Confirmed
to fire by appending a stale line and re-running the audit. Only that direction is checked —
the reverse is already reported every session by `hooks-installed`.

## Verification improvement

Generalised as L-005 in [../LESSONS.md](../LESSONS.md) — *a gate that requires manual
enablement is off by default; verify the gate, not just the tests.*

Closing this one produced its second half, L-020 — *a doc that restates a checked fact
outlives the fact.* The check here was right all along; five documents describing it were
not, and the one an agent actually reads led it to report the gate as off on the very day it
started running.
