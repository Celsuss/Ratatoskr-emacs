# FAIL-0024 — HN articles read "article not fetched (timed out)": url.el does not fall back from an unrouted IPv6 address

| | |
|---|---|
| **Date found** | 2026-10-06 |
| **Severity** | MEDIUM |
| **Category** | integration, verification-gap |
| **Area** | `lisp/init-elfeed-hn.el` (`rata-elfeed-hn--retrieve`) |
| **Origin** | introduced the same day by the feature itself (D-023); found by the operator on first use |
| **Status** | FIXED — fetching goes through curl when it is on PATH |

## Symptoms

Opening an HN entry in elfeed drew the comments, but the article section always said
`article not fetched (timed out)`. The full `are-verify full` run had passed an hour earlier.

## Mechanism

The laptop's network hands out a global IPv6 address by router advertisement but does not
route IPv6: `curl -6` fails for every host. `url-retrieve` connects to the first address
the resolver returns, IPv6 when the host publishes an AAAA record, and waits out the
connect timeout before it would try IPv4 — longer than the module's 20 s timeout. curl
races the two families (happy eyeballs) and is on IPv4 within milliseconds.

Probed on 8 front-page article URLs: url.el timed out on the four with real AAAA records
(Cloudflare and Fastly fronted), took 9.6 s on a fifth, and was fast only on hosts with no
AAAA. `hn.algolia.com` publishes none, which is why comments worked and articles did not.
Even a site that answers 403 at once "timed out": url.el never reached HTTP.

## Why the gates missed it

Every test answers from a fixture behind `rata-elfeed-hn--retrieve` — by design, nothing in
`tests/` may reach the network — so the transport was never exercised. The live check that
was run (one Algolia request, while debugging FAIL-0023) happened to hit a host with no AAAA
record.

## Fix

`rata-elfeed-hn--retrieve` runs `curl --location --compressed --max-time --max-filesize`
when `rata-elfeed-hn-curl-program` is on PATH (elfeed itself prefers curl for feeds), and
keeps url.el as the fallback. Output parsing is pure (`rata-elfeed-hn--curl-result`, tested
on each exit path); the process plumbing is tested against `tests/fixtures/hn/fake-curl`.
After the fix the same 8 URLs resolve in ≤ 2 s each: 6 articles, a PDF rejected by type,
and niemanlab's real 403.

Not fixed, and not this repo's to fix: the network's IPv6. Anything else in Emacs that
uses url.el against an AAAA host on this network stalls the same way (package.el, eww).

Related: L-058, FAIL-0017 (another feature whose fixtures matched an assumption the live
service did not), D-023.
