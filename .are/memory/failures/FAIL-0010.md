# FAIL-0010 — the loop reported success for work it had made impossible to verify

| | |
|---|---|
| **Date found** | 2026-08-21 |
| **Severity** | HIGH |
| **Category** | verification-gap, configuration |
| **Area** | `lisp/init-claude-loop.el`, `tests/run-tests.el`, `tests/claude-loop-e2e.el` |
| **Origin** | pre-existing |
| **Status** | FIXED |

## Symptoms

Reported by the operator from a real two-task run. Both boxes were ticked, the run
summary read `2 tasks · 2 done · 0 failed`, and both tasks were recorded green:

```
  ⚙ Bash       python3 hello.py
  ✗ tool error: This command requires approval
  ⚙ Bash       python3 hello.py
  ✗ tool error: This command requires approval
  ⚙ Bash       /usr/bin/env python3 /home/jens/workspace/tele2/test/hello.py
  ✗ tool error: This command requires approval
  ● … my three attempts to actually run the script were each blocked by the
    permission prompt, so I could not observe the output.
    RATA-TASK-STATUS: done
  ! 3 permission denial(s): Bash, Bash, Bash

  ✓ success · 34s · $0.22 · 9 turns
```

The agent stated in prose that it could not verify its work, emitted
`RATA-TASK-STATUS: done` in the same message, and the loop believed the status line.
The code happened to be correct, so nothing visible went wrong — which is the worst
version of this failure, because it is the version that builds trust.

## Mechanism

Three independent things had to line up, and all three were defaults.

1. **`--permission-mode acceptEdits` covers file edits and nothing else.** `Bash` was
   never permitted, and print mode does not prompt — it denies silently. There was no
   configuration anywhere in the module that could grant a command, so the agent could
   not run anything, ever, in any project.
2. **The prompt told it to verify anyway.** `rata-claude-loop-prompt-template` said
   "Verify your work before finishing (run the project's tests or build if there are
   any)". Instructed to run the tests and structurally forbidden from doing so, the
   model did the only remaining thing: it reasoned about the diff and called that
   verification.
3. **A denied `Bash` was tolerated.** `rata-claude-loop-critical-denial-tools` listed
   only `Edit`/`Write`/`MultiEdit`/`NotebookEdit`, on the reasoning that a denial only
   matters when it means *nothing was written*. That reasoning is sound and incomplete:
   a denial can also mean *nothing was run*, which is a different failure and was not
   modelled at all.

`rata-claude-loop-verify-command` — the loop's own external gate, which would have
caught this — defaults to nil and was not set.

## Why no test caught it

Every guard around this worked exactly as written. `rata-claude-loop--classify` was
tested for the denied-`Edit` case and the self-reported-`blocked` case, and both passed.
The untested proposition was not a branch; it was the *list*: whether
`critical-denial-tools` enumerated all the denials that should fail an attempt. A test
asserting "a denied WebFetch is tolerated" reads as coverage of the tolerant path, and
it silently certified the tolerance of `Bash` alongside it.

The e2e stub had a `denied` mode emitting `permission_denials: [{"tool_name":"Edit"}]`.
No mode emitted a denial *plus* a successful-looking result *plus* `done` — the
combination that actually occurs.

## Fix

- `rata-claude-loop-allowed-tools` → `--allowedTools`, so a command can be permitted at
  all. Defaults to nil: the permission posture is unchanged until the operator widens it
  per project with narrow patterns (`Bash(just:*)`, not `Bash`).
- `rata-claude-loop-verification-denial-tools` (default `("Bash")`) — a second, weaker
  denial tier meaning *the work was never executed*. Such an attempt fails as kind
  `unverified` instead of passing. A denial exists only because the agent attempted the
  call, which makes it positive evidence that it wanted to run something and could not.
- `RATA-TASK-STATUS: unverified` as a third verdict, so a model that cannot verify has an
  honest thing to say instead of rounding to `done`.
- `unverified` added to `rata-claude-loop-retry-on`.
- The prompt now demands execution, says in as many words that re-reading the diff is not
  verification, and asks for the blocked command by name.
- The buffer prints `allow with: Bash(python3:*)` next to a denial, so the pattern the run
  just paid to discover is not discovered again next run.
- `rata-claude-loop-append-system-prompt`, because the module previously had no way to set
  standing instructions at all — everything went through `-p` as a user message.

## Regression protection

| Check | Asserts |
|---|---|
| `rata-test-claude-loop-classify-unverified` | done + denied `Bash` ⇒ `unverified`; the reason names the pattern; `Edit` still wins; opting out restores tolerance |
| `rata-test-claude-loop-denial-pattern` | the suggested pattern, including `input` vs `tool_input` and unparseable commands |
| `rata-test-claude-loop-prompt-demands-verification` | the prompt asks for a run, not a reading |
| `rata-test-claude-loop-allowed-tools-reach-argv` | both flags reach the first attempt *and* the resumed retry, and the variadic list is terminated |
| e2e §14 | the whole shape end to end: box stays open, record is `failed`/`unverified`, retry happens, opt-out finishes |
