# FAIL-0020 — `just batch` ran elpaca on its post-init path, so the harness reported load-order warnings a real startup never produces

| | |
|---|---|
| **Date found** | 2026-09-13 |
| **Severity** | MEDIUM |
| **Category** | verification-gap, self-inflicted |
| **Area** | `just/emacs.just` `batch`, `scripts/check-startup.sh`, `tests/run-tests.el` |
| **Origin** | pre-existing in the harness since it was written; visible since at least 2026-08-31 (session memory #1804 recorded the transient warning as "pre-existing"), red in `are-verify full` since `c76feb0` changed the queue composition |
| **Status** | FIXED |

## Symptoms

`just batch-strict` failing `are-verify full` on:

```
Error (use-package): Cannot load nerd-icons-corfu
Warning (emacs): transient loaded before Elpaca activation
```

Deterministic — three consecutive runs, identical. Assumed in the task brief to be a
consequence of the stale 30.2 artifacts (FAIL-0015). Both survived the rebuild.

Meanwhile a real startup was clean: a throwaway `--fg-daemon` from the same checkout,
on the same artifacts, had `rata--failed-modules` nil, `transient` loaded from
`elpaca/builds`, and nothing in `*Warnings*` but elpaca's `core-date` line.

## Mechanism

`emacs --batch` skips the init files, so by the time `-l init.el` runs, Emacs has already
stamped `after-init-time`. elpaca branches on that variable in six places
(`elpaca.el:242, 419, 553, 665, 745, 794`): with it set, a queue is not of type `init`,
`elpaca--enqueue` skips duplicate detection, and — the one that bit —
`elpaca--finalize-queue` fires as soon as a queue's processed count catches up with its
length (`elpaca--finalize`). With `elpaca-queue-limit 5` (`init.el:13`), the last orders
declared into a queue are still *throttled* at that moment, so the queue's deferred
`use-package` bodies run while `nerd-icons-corfu` and `transient` are still `queued`:
the first `require` fails outright, the second finds Emacs 31's **built-in**
`transient.elc` (backtrace: `provide(transient)` from `/usr/share/emacs/31.1/lisp/`),
and when elpaca later activates its own copy it correctly warns that the feature was
already loaded.

Which orders get stranded depends on where the throttle boundary falls, i.e. on the
number of orders in the queue. `c76feb0` removed `corfu-terminal` and `popon` from that
queue, which is why the symptom set changed shape (the pre-guard tree stranded `cape`
too) and why the check was green on some days and red on others with no relevant commit
in between. Binding `elpaca-queue-limit` to nil made the run clean, which is what
isolated the throttle.

None of this happens in a real startup: `after-init-time` is nil until init.el has
finished, queues are `init`-typed, and `elpaca-process-queues` runs from
`after-init-hook` with the throttle draining in order.

## Remediation

`just batch` now passes `--eval "(setq after-init-time nil)"` **before** `-l early-init.el`,
and `tests/run-tests.el` sets the same before loading the config. Verified equivalent
on everything measurable: 677 features and 39 `init-*` modules loaded either way,
197/197 orders finished, `rata--failed-modules` nil — and zero warnings.

Considered and rejected: clearing `elpaca-queue-limit` in the harness. That hides the
symptom by removing the throttle rather than putting elpaca on the path the daemon takes;
the `after-init-time` fix is the faithful one, because the harness's whole claim is "this
is what a startup does".

## Why nothing caught it

`check-startup.sh` did exactly what FAIL-0012 built it to do — it read the output and
failed. The gap was one step earlier: nobody had compared the harness's warnings with a
real startup's, and the two symptoms read like the FAIL-0012 class (a module requiring
too early), so the diagnosis went looking for a `require` in `lisp/`. The daemon check was
what broke the assumption. When a harness reports a load-order fault, the first question
is whether the *harness* is on the same path as the thing it simulates (L-048).

## Regression protection

`just batch-strict` itself, now that it runs on the init path: it fails on the same two
patterns as before, and would fail again if the `--eval` were dropped (confirmed by
running the old invocation against the same tree). No separate test — the harness is the
test.
