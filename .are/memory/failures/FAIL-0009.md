# FAIL-0009 — leader keys bound inside a deferred `use-package :config` are never created

| | |
|---|---|
| **Date found** | 2026-08-20 |
| **Severity** | MEDIUM |
| **Category** | configuration, verification-gap |
| **Area** | `lisp/init-dev.el`, `lisp/init-evil.el`, `tests/run-tests.el`, and 20 further modules |
| **Origin** | pre-existing |
| **Status** | RESOLVED 2026-08-24 — all dead global keys hoisted to top-level `with-eval-after-load 'general`; probe reports 0 dead; exhaustive gate `rata-test-all-global-leader-keys-live-after-init` added |

## Symptoms

Reported by the operator from a live session: pressing `SPC p f` says the key is
**undefined**, even though `lisp/init-dev.el` contained

```elisp
(use-package consult-projectile
  :after (consult projectile)
  :commands (consult-projectile-find-file consult-projectile-ripgrep)
  :config
  (rata-leader
    :states '(normal visual)
    "pf"  '(consult-projectile-find-file :which-key "find file")
    "ps"  '(consult-projectile-ripgrep :which-key "ripgrep project")))
```

The binding is written, the file loads without error, every test passed.

## Mechanism

`:config` is not evaluated when the module is loaded — it is evaluated when the *package*
loads. `consult-projectile` is deferred (`:after`, `:commands`, no `:demand`) and nothing in
the config ever loads it, so the `rata-leader` call never ran and the key was never created.
`:commands` autoloads only make the *command* callable (via `M-x`); they say nothing about
the key. Invoking `M-x consult-projectile-find-file` once loads the package and *then*
`SPC p f` starts working for the rest of that session — which is why the bug feels
intermittent.

The aggravating detail: the sibling `use-package projectile` block had the identical shape,
yet `SPC p S` *did* work. Not by design — `lisp/init-dashboard.el` sets
`dashboard-projects-backend` to `projectile` and dashboard is `:demand t`, so rendering the
dashboard's projects section pulled projectile in at startup and ran its `:config` as a side
effect. Every projectile leader key in the config depended on that accident. Changing one
`setq` in an unrelated module would have silently deleted six keybindings.

## Why nothing caught it

`tests/run-tests.el` had two keybinding tests, and both check the *source text*:

- `rata-test-keybindings-no-lambdas` — no anonymous lambdas in a `rata-leader` form.
- `rata-test-keybindings-all-commandp` — every bound symbol satisfies `(commandp sym t)`.

The docstring of the second one even explains that it uses the autoload-tolerant form "so
deferred packages (loaded via `:commands`) pass correctly". That is exactly the case that is
broken at runtime: the symbol is a valid command *and* the key does not exist. The tests
asserted the binding was well-formed, never that it was reachable. Same shape as
L-003…L-006: a check that does not reach as far as its name suggests.

## Fix applied

`lisp/init-dev.el` — the `rata-leader` call moved out of both `:config` blocks to a single
top-level `(with-eval-after-load 'general …)`, the pattern already used for `esup` in the
same file. Load behaviour of the packages is unchanged; only the moment the keys are created
moved to init time. `lisp/init-evil.el` — dropped the stale `"pp"` binding so `SPC p p`
could be reused (`SPC p b` already covers project buffers).

## Regression protection

`rata-test-keybindings-live-after-init` in `tests/run-tests.el`. The ERT suite already runs
against a fully loaded config, so the test resolves each key the way evil does:

```elisp
(lookup-key (evil-get-auxiliary-keymap general-override-mode-map 'normal) (kbd "SPC p f"))
```

`rata-leader` binds through general with `:states`, so bindings land in the normal-state
auxiliary keymap of `general-override-mode-map` — not the global map, which is why a plain
`key-binding` finds nothing in batch. Confirmed to fire: pointing the new
`with-eval-after-load` at a feature that never loads makes the test fail with
`SPC p p → UNDEFINED` (per L-008, the check was watched failing before being trusted).

`rata-test--must-be-live-keys` is a curated table, not exhaustive — extend it whenever a
binding turns out to have been dead.

## Wider instance count — RESOLVED 2026-08-24

The probe (`.are/memory/failures/FAIL-0009-probe.el`) measured **142 live / 113 dead** of 255
global (non-`:keymaps`) leader keys (more than the 86 first recorded — `init-khoj`, `init-k8s`,
`init-irc` were added since). Every dead key was hoisted out of its deferred `use-package`
`:config`/`:init` into a top-level `(with-eval-after-load 'general (rata-leader ...))` block
(the pattern already proven for `SPC p` in `init-dev.el`). The probe now reports **255 live /
0 dead**, and its logic is absorbed into the ERT gate as
`rata-test-all-global-leader-keys-live-after-init` so the regression cannot silently return.

Historical snapshot of what was dead before the fix (of 255 global keys, 113 dead):

| Keys | Module | Package |
|---|---|---|
| `SPC g g`, `g s`, `g b`, `g l`, `g f`, `g d`, `g F` | `init-dev.el` | magit, forge |
| `SPC L …` (10 keys) | `init-dev.el` | lsp-mode |
| `SPC d …` (9 keys) | `init-lang.el` | dap-mode |
| `SPC o …` (~40 keys) | `init-org.el` | org, org-roam and friends |
| `SPC t t`, `t T` | `init-dev.el` | vterm-toggle |
| `SPC a …` | `init-casual.el`, `init-docker.el`, `init-k8s.el`, `init-khoj.el`, `init-llm.el`, `init-jupyter.el` | various |

Not all 86 are equally wrong — a key whose package is loaded by the mode it belongs to is
merely late, not broken. But the top-level entry points (`SPC g g` for magit status,
`SPC o a` for the agenda) have no other trigger, so the first press of the session does
nothing. Fixing them is a behavioural change across ~20 modules and was **not** done in the
session that found this: it is left as an operator decision, not an autonomous edit.
