# FAIL-0016 — The Jira buffers' emacs state sat in a `:config` block keyed on a feature nothing ever loads, so every jira.el key was shadowed by evil

| | |
|---|---|
| **Date found** | 2026-09-08 |
| **Severity** | MEDIUM |
| **Category** | configuration, verification-gap |
| **Area** | `lisp/init-jira.el`, `tests/run-tests.el`, `docs/jira-cheatsheet.org` |
| **Origin** | pre-existing — present since `init-jira.el` was written |
| **Status** | FIXED |

## Symptoms

Reported by the operator while reading the cheat sheet that had just been written for
this module: pressing `l` in `*Jira Issues*` to open the query transient moved the cursor
one column right instead. That is `evil-forward-char`, i.e. the buffer was in evil
**normal** state, not the emacs state `init-jira.el` claims to give it.

The blast radius is the whole module, and it is worth recording precisely, because
"shadowed by evil" undersells it. Measured in a `jira-issues-mode` buffer with the
registration removed (evil normal state):

| Key | Resolved to |
|---|---|
| `l` `h` | `evil-forward-char` / `evil-backward-char` |
| `?` | `evil-search-backward` |
| `f` `T` | `evil-find-char` / `evil-find-char-to-backward` |
| `e` `W` | `evil-forward-word-end` / `evil-forward-WORD-begin` |
| `H` `G` `n` | `evil-window-top` / `evil-goto-line` / `evil-search-next` |
| `c` `C` `I` `O` `p` | **`ignore`** — evil-collection blanks them in tabulated-list buffers, so they did nothing at all |
| `M-n` `M-p` | `jira-issues-next-page` / `-previous-page` — reached jira.el, and permanently useless on Server/DC (L-038) |
| `q`, `g r` | `tablist-quit`, `tablist-revert` via evil-collection's `g` prefix |

So not one documented Jira action was reachable by its documented key — including `?` and
`l`, the two transients that are supposed to *be* the module's documentation. `SPC J j`
opened the buffer correctly and nothing after that did what the docs said, which is the
worst shape for this: the entry point works, so the module looks configured.

## Mechanism

`use-package`'s `:config` expands to `(with-eval-after-load 'jira ...)`. The feature
`jira` is **never loaded in this configuration**, so the body never ran. Three facts
compose:

1. Elpaca loads `jira-autoloads.el` at activation, which defines
   `(autoload 'jira-issues "jira-issues")` and `(autoload 'jira-tempo "jira-tempo")` —
   the *sub*-files, because that is where the `;;;###autoload` cookies are.
2. `use-package`'s `:commands` handler guards its own stub with
   `(unless (fboundp 'jira-issues) (autoload #'jira-issues "jira" ...))`. The symbol is
   already fbound by (1), so use-package's stub — the one that would have loaded `jira` —
   is skipped.
3. Nothing in the package requires `jira`: `jira.el` is an umbrella that requires
   `jira-issues`, `jira-export` and `jira-tempo`, and none of them requires it back.

So `M-x jira-issues` loads `jira-issues.el` and its dependency web, provides
`jira-issues`, and leaves `(featurep 'jira)` nil forever. Measured after a full init:

```
featurep jira        : nil
jira-issues fn cell  : (autoload "jira-issues" nil t nil)
emacs-state-modes has jira-issues-mode : nil
```

The `:custom` block in the same form is unaffected, which is why the module looked
healthy: `:custom` compiles to `custom-theme-set-variables` under the `use-package`
theme, which *records* a value for a not-yet-declared variable and applies it when the
`defcustom` finally loads. `jira-issues-max-results` was correctly 100 after the require.
Only `:config` is load-gated, and only `:config` was dead.

## Why nothing caught it

This is FAIL-0009 one layer down, and the protection built for FAIL-0009 does not reach
it. `rata-test-all-global-leader-keys-live-after-init` is exhaustive over
`rata-leader` forms, and `SPC J j` / `SPC J t` were live — they are already at top level
in this module. The dead code was not a keybinding at all; it was the evil-state
registration that makes the *package's own* keymap reachable, and no test in the suite
asserted a major mode's initial evil state.

The three existing jira tests all pass through `(require 'jira-api)` /
`(require 'jira-issues)` and assert on variables, so they never observed that
`with-eval-after-load 'jira` had not fired. Nothing anywhere required `jira`, so nothing
noticed that requiring it was the trigger for a block of configuration.

The generalisable gap: **a `:config` block is only as live as the feature it is keyed on,
and for a multi-file package the feature named in `use-package` is often not the feature
the autoloads pull in.** An umbrella file that only `require`s its siblings is never
loaded by anything.

## Remediation

Two steps, in the same session, because fixing the dead `:config` exposed a design question
the operator then answered differently.

**Step 1 — the actual defect.** The `evil-set-initial-state` loop moved out of `:config` to
top level, inside `(with-eval-after-load 'evil ...)`, next to the leader keys that are there
for the FAIL-0009 reason. That is the correct home on its own merits: the form needs `evil`
and nothing else, it only pushes mode symbols onto `evil-emacs-state-modes`, and the list is
read when the major mode activates — long after this file has run. The `jira` feature never
has to load for it to be right.

**Step 2 — the design, on operator instruction (D-015).** With emacs state actually working,
the operator did not want it: *"I would like to keep using EVIL mode inside the jira buffer.
If there is any keybinding conflicts then we need to fix those."* So the module now keeps
evil normal state and mirrors jira.el's own keys under the local leader `,`, built with
`lookup-key` out of the package's mode maps. The full reasoning, and why the maintenance cost
L-017 warned about does not land, is in D-015.

The `:config` lesson survives both steps intact and is the durable part: whatever configures
these buffers, it may not live in `use-package jira`'s `:config`. The module comment says so,
because the code reads like it belongs there.

## Regression protection

Three tests in `tests/run-tests.el`, all asserting the *observable* end state rather than
the shape of the source, because the source looked correct throughout:

- **`rata-test-jira-buffers-keep-evil-and-mirror-keys`** — a real buffer in
  `jira-issues-mode` reports `evil-state` `normal` (evil is live, `j` is `evil-next-line`),
  `(key-binding ", l")` is `jira-issues-menu`, `RET` is not `evil-ret`, and what
  evil-collection supplies (`q`, `g r`, `m`) still resolves. Same for `jira-detail-mode`,
  including that `TAB` is still `magit-section-toggle`. This is the test that would have
  caught the original defect: from the user's side, a mirror that was never installed and a
  `:config` that never ran are the same thing — a key that does nothing.
- **`rata-test-jira-mirrored-keys-exist-upstream`** — for every mirror entry, the upstream
  key still resolves in jira.el's map *and* the `,` suffix resolves to a command in a live
  buffer. Because the mirror is built by `lookup-key`, an upstream rename would otherwise
  drop one leader key silently.
- **`rata-test-use-package-config-blocks-can-run`** — the generalisation, see L-039: for
  every `use-package` in `lisp/` with both `:commands` and `:config`, the autoloaded file
  must actually reach the named feature. This is the check that catches the *next* package
  with an unreachable umbrella, not just jira.

All require `jira-issues` rather than `skip-unless`-ing it, for the reason in L-038: a
permanently skipped test reads as coverage.

Both new checks were confirmed to discriminate rather than watched passing (L-034):

| Simulated state | Result |
|---|---|
| registration removed from a live init (the pre-fix state) | `jira-issues-mode` yields `evil-state=normal`, `l` → `evil-forward-char` — the operator's report reproduced exactly |
| a dead `:config` block re-added to `use-package jira` | `rata-test-use-package-config-blocks-can-run` FAILS, naming the package and the file its command really autoloads |
| current tree | 73/73 ERT pass; `, l` → `jira-issues-menu`, `j` → `evil-next-line` |
