# FAIL-0021 — An ERT test turned on `jira-tempo-mode`, which makes a live worklog request, which decrypts `~/.authinfo.gpg`; the suite either prompted for a passphrase or silently called the corporate Jira

| | |
|---|---|
| **Date found** | 2026-09-13 |
| **Severity** | HIGH |
| **Category** | verification-gap, safety |
| **Area** | `tests/run-tests.el` (`rata-test-jira-mirrored-keys-exist-upstream`), `lisp/init-jira.el` |
| **Origin** | introduced by `593469f` (2026-09-08) with the key mirror |
| **Status** | FIXED |

## Symptoms

Found while re-running ERT on the init path (FAIL-0020). At test 69 of 103:

```
[Jira Tempo Call]: GET worklogs/user/
Decrypting /home/celsuss/.authinfo.gpg...0%
Passphrase for <key id> <name> <email>: error in process filter: End of file during parsing: Error reading from stdin
```

and Emacs exited 255 — **before** ERT's summary line. The earlier `are-verify full` log
from the same day shows the identical tail: `recipe 'test-ert' failed ... exit code 255`
after a passphrase prompt. Every ERT run since 2026-09-08 has ended this way whenever
gpg-agent did not hold the key; the operator's "2/103 FAILED" reading came from the two
agent-shell lines printed before the abort, not from a completed run.

When gpg-agent *did* hold the key, the request went out — to the instance named in
`local.el` — and the run continued. Two rules broken at once: nothing in `tests/` may
contact a network service (AGENTS.md §5), and nothing autonomous may read
`~/.authinfo.gpg` (SAFETY_RULES §1).

## Mechanism

The test does `(funcall mode)` for each of jira.el's three modes to read the live keymap.
`jira-tempo-mode` (`jira-tempo.el:180-183`) adds `jira-tempo--refresh` to
`tabulated-list-revert-hook` and calls `tabulated-list-revert` as part of turning on;
the refresh is `jira-tempo--api-get-worklogs`, a real request. `jira-api-call`
(`jira-api.el:213`) resolves the token through `auth-source` first, which is the GPG
decrypt. In batch, `read-passwd` reads stdin: EOF when redirected, a blocking prompt on a
TTY.

The 2026-09-08 session verified the test on a machine where gpg-agent had the key cached,
so the request simply succeeded and nothing looked wrong. It was the *absence* of a
network stub that was invisible, not the presence of a call.

## Remediation

- The test stubs `jira-tempo--refresh` with `cl-letf` around the one `funcall` that
  triggers it; the keymap is all it reads.
- **Harness-wide guard**: `tests/run-tests.el` overrides `jira-api-call` **and**
  `jira-api-tempo-call` after the config loads to signal `rata-test: ... would reach the
  network; stub it in the test`, so any future test that reaches either fails loudly at
  the call rather than at a passphrase prompt. A test that legitimately needs a request
  shadows it with its own `cl-letf`. The first version guarded only `jira-api-call`, on
  the assumption that jira.el had one chokepoint; a probe that turned on `jira-tempo-mode`
  with the guard in place still reached the passphrase prompt, because Tempo goes through
  its own `jira-api-tempo-call` (`jira-api.el:273`). The probe is what found the second
  one.

After the fix: 103 tests in 1.1 s, no prompt, exit by ERT's own verdict.

## Why nothing caught it

The suite has no general "no network" fence — the rule lives in prose. jira.el is the
only module whose tests instantiate real major modes with side effects on activation, and
the one that reverts on activation happens to be the third of three. The abort also
masked itself: exit 255 with no summary line reads like "some tests failed", and the two
agent-shell failures printed just before it gave that reading a plausible cause.

## Regression protection

The two overrides in `tests/run-tests.el`. Verified the L-034 way, against the real call
path: with the harness bootstrap loaded and no per-test stub, `(jira-tempo-mode)` in a
temp buffer signals `rata-test: 'jira-api-tempo-call' (GET worklogs/user/) would reach
the network` — and did *not* until the second override existed.
