# FAIL-0013 — A merge conflict marker was committed into `init-org.el` and every gate stayed green

| | |
|---|---|
| **Date found** | 2026-09-01 |
| **Severity** | MEDIUM |
| **Category** | repo-hygiene, verification-gap |
| **Area** | `lisp/init-org.el`, `scripts/are-audit.sh` |
| **Origin** | introduced by merge commit `b510337` |
| **Status** | FIXED — marker removed; `are-audit` check `no-conflict-markers` added |

## Symptoms

None visible from the tooling. `just are-verify fast` reported PASS on lint,
claude-loop-e2e and are-audit at the start of the session that found this. The marker
was noticed only because the task happened to require reading the bottom of the file.

```
    "iop" '(org-id-get-create :which-key "id property (roam node)")))
>>>>>>> 4f0efe70a584b93e9ac57f6f5f271475aba6559d

(provide 'init-org)
```

## Mechanism

Two things had to be true at once.

**The marker is silent to every existing check.** `just lint` is a shell script that does
not read Elisp. `just compile` byte-compiles with no packages on `load-path` and exits 0
regardless (FAIL-0003). The keybinding tests in `tests/run-tests.el` *do* `read` the file
form by form — but `>>>>>>>` and `4f0efe70a584b93e9ac57f6f5f271475aba6559d` are both
perfectly legal Elisp symbols, so the reader raises nothing and
`rata-test--extract-leader-bindings-from-file` walks straight past them.

**Its runtime effect hides behind `provide`.** The marker sits *after*
`(provide 'init-org)`. Loading the file therefore registers the feature, and only then
evaluates `>>>>>>>` as a variable reference and signals `void-variable`.
`rata-load-module` catches that and logs it, so the module reports as present while the
tail of it never ran. Here nothing followed the marker but `provide`, so no behaviour was
lost — that was luck, not design. The same marker fifty lines higher would have silently
dropped every `rata-leader` form below it, which is FAIL-0009's failure mode arriving by a
different road.

The resolution itself was correct: `b510337` kept the superset of both parents. Only the
marker line survived the edit.

## Fix

1. Removed the marker line from `lisp/init-org.el`.
2. Added `are-audit` check **`no-conflict-markers`**: `git ls-files` over `*.el`, `*.sh`,
   `*.md`, `*.org`, `*.yml`, `*.yaml` and `justfile`, grepping for a line starting
   `<<<<<<< ` or `>>>>>>> `, or a line that is exactly seven `=`. Verified in both
   directions — it passes on the cleaned tree and fails on a planted marker in
   `lisp/` and in `.are/memory/LESSONS.md`.

   Two paths are exempt: `scripts/are-audit.sh`, which has to contain the patterns in
   order to search for them, and `.are/memory/failures/`, because reproducing the
   offending bytes as evidence is what a record is *for*. That exemption was not
   foresight — the pre-commit hook failed this very commit on **this file**, whose
   Symptoms block above quotes the marker at column 0. Both exempt paths are prose or
   tooling and are never loaded as configuration, so a real conflict in one is cosmetic
   rather than a module that half-executes. Everything else stays in scope, `LESSONS.md`
   included, which is why L-030 discusses markers inline rather than in a fenced block.

Because `are-audit` runs in `are-verify fast`, this is now caught at the cheapest tier and
by the pre-commit hook.

## Why the check is repo-wide rather than a test

An ERT test would have to load the file to notice, and loading is exactly what hides the
problem. A conflict marker is a property of the *bytes on disk in tracked files*, not of
any module's behaviour, so it belongs with `stray-files` and `docs-paths` in the audit —
the same class as FAIL-0007.
