# FAIL-0014 — The Claude ACP adapter was pinned to a name upstream had abandoned, and installed only on Arch

| | |
|---|---|
| **Date found** | 2026-09-03 |
| **Severity** | MEDIUM |
| **Category** | configuration, environment-drift, verification-gap |
| **Area** | `lisp/init-llm.el`, `justfile` `install-deps`, `.are/knowledge/INTEGRATIONS.md` |
| **Origin** | pre-existing — the pin dates from the original `agent-shell` wiring; upstream renamed the adapter around 2026-03 |
| **Status** | FIXED — pin updated to `claude-agent-acp`, adapter installed with bun, drift test and audit check added |

## Symptoms

Reported by the operator: `SPC a i c c` on the Ubuntu laptop gives

```
agent-shell--start: Executable "claude-code-acp" not found. Do you need
(add-to-list 'exec-path "another/path/to/consider/")?  See
https://github.com/agentclientprotocol/claude-agent-acp for installation.
```

`SPC a i c p` (Pi) works on the same host, and Claude Code works on the operator's Arch
machine. That asymmetry is what made it look like an `exec-path` problem. It was not:
`~/.bun/bin` and the nvm bin directory are both in the login zsh `PATH`, and
`exec-path-from-shell` runs for GUI frames (`lisp/init-system.el:18-25`).

## Mechanism

Three independent causes stacked, which is why no single check caught it.

**1. The install path was Arch-only.** `justfile:104` carries
`aur_pkgs=(claude-code-acp gomodifytags)`. On Arch, `just install-deps` pulls the adapter
from the AUR. Ubuntu has no AUR, so nothing ever installed it here — and `install-deps` is
documented as never run on this host, so its contents were never a statement about this
machine. Pi was unaffected because `pi-acp` came from `bun install -g` and genuinely is on
`PATH`.

**2. An npm name collision hid that.** `npm ls -g` reported `claude-code-acp@0.1.1`, so the
adapter looked installed. That package is an unrelated third party's
("Claude Code agent for Zed Editor via Agent Client Protocol", a different author) and its
`bin` is **`cc-acp`**:

```sh
$ npm view claude-code-acp version bin
version = '0.1.1'
bin = { 'cc-acp': 'dist/index.js' }
```

It never provided a `claude-code-acp` executable at all. `npm ls -g` naming a package is not
evidence that any particular executable exists.

**3. The pin outlived an upstream rename by five months.** `lisp/init-llm.el` set

```elisp
(agent-shell-anthropic-claude-acp-command '("claude-code-acp"))
```

with the comment "Both values are agent-shell's own defaults; they are spelled out because
the adapter name is the one thing that breaks when an upstream renames it." By 2026-09-03
that was false for the Claude side. The installed `agent-shell`
(`elpaca/sources/agent-shell/agent-shell-anthropic.el:110-111`) defaults the option to
`'("claude-agent-acp")`; upstream had moved from `@zed-industries/claude-code-acp` (frozen at
0.16.2, untouched since 2026-03-26) to `@agentclientprotocol/claude-agent-acp` (0.73.0,
published 2026-09-01). The pin's stated purpose was to make a rename *visible*, and instead
it **suppressed the default that would have healed it** — because nothing compared the pin to
upstream. Had the pin been absent, the config would have started working the moment the
package was updated.

## Why nothing said PASS-but-broken

Nothing in `tests/` execs an ACP adapter, so the adapter's name and existence were outside
every gate. `just are-verify full` passed, `rata-test-keybindings-live-after-init` passed —
that test asserts `SPC a i c c` resolves to `agent-shell-anthropic-start-claude-code`, which
it did. The command was live; only the process it spawns did not exist. This is the
FAIL-0009 / FAIL-0011 shape a third time: the suite was green on a real contract that was
one level shallower than the defect.

The knowledge base was worse than silent — it was *correct and ignored*.
`.are/knowledge/INTEGRATIONS.md:18-19` already recorded "AUR package on Arch; not present on
this Ubuntu host" and "`SPC a i c p` works here and `SPC a i c c` does not". A known-missing
dependency had been written down as a settled property of the host rather than as a defect
with a fix, and no check turned it back into a signal.

## Fix

1. `lisp/init-llm.el` — pin updated to `'("claude-agent-acp")`; the comment corrected to stop
   claiming it is trivially upstream's default and to name the test that now enforces it.
2. Adapter installed: `bun install -g @agentclientprotocol/claude-agent-acp`, matching how
   `pi-acp` is installed (lands in `~/.bun/bin`, so it survives an nvm version switch; the
   `dist/index.js` shebang is `#!/usr/bin/env node`, so it still runs under node 22 as its
   `engines: node >=22` requires). The impostor was removed with
   `npm uninstall -g claude-code-acp`.
3. Verified by handshake rather than by inspection — one line of stdio, per L-031:

   ```
   $ printf '%s\n' '{"jsonrpc":"2.0","id":0,"method":"initialize","params":{"protocolVersion":1,
     "clientCapabilities":{"fs":{"readTextFile":true,"writeTextFile":true}}}}' | claude-agent-acp
   {"jsonrpc":"2.0","id":0,"result":{"protocolVersion":1,...,"agentInfo":{
     "name":"@agentclientprotocol/claude-agent-acp","title":"Claude Agent","version":"0.73.0"},
     "authMethods":[],...}}
   ```

   `authMethods: []` confirms the CLI's web login is already sufficient — no key in this repo.
4. A dependency conflict was anticipated and checked rather than hoped away: the new adapter
   pins `@agentclientprotocol/sdk` at exactly 1.4.0 and `zod@^4`, while `pi-acp` needs
   `^0.26.0` and `zod@^3.25`. bun hoisted the new versions and gave `pi-acp` nested copies
   (`~/node_modules/pi-acp/node_modules/{@agentclientprotocol/sdk@0.26.0,zod@3.25.76}`), so
   Pi still handshakes. Fixing one agent by breaking the other was the live risk here.

## Regression protection

- `rata-test-acp-adapter-commands-match-upstream` (`tests/run-tests.el`) — compares each
  pinned adapter command against `agent-shell`'s own `defcustom` standard value, so the next
  upstream rename fails a test instead of a keybinding. Verified in both directions: it fails
  with `ACP adapter pins have drifted from upstream: agent-shell-anthropic-claude-acp-command
  is pinned to ("claude-code-acp") but agent-shell now defaults to ("claude-agent-acp")` when
  the old name is put back, and it refuses a `nil` standard value so it cannot pass vacuously.
- `are-audit` check `acp-adapters-on-path` — warns (never fails) when an adapter named in
  `init-llm.el` is not on `PATH`, so a missing adapter surfaces in the `fast` tier at session
  start instead of when the leader key is pressed. Reads the names out of the config so it
  cannot drift, and warns if it extracts none. Verified in both directions.

## Still open

`justfile:104` still lists `claude-code-acp` in `aur_pkgs`, by operator decision (scope).
The Arch machine's `just install-deps` therefore installs the abandoned adapter under a name
nothing references any more, and Claude Code will break there — the mirror image of this
record. `acp-adapters-on-path` will warn about it at session start on that host, which is
mitigation, not a fix. Fixing it means moving the adapter out of `aur_pkgs` into a bun/npm
step. `README.org:83` likewise still calls the dependency "(AUR)".

## Lessons

- L-033 — an Arch-only install path means "not installed" everywhere else, silently; and a
  pinned third-party binary name is only safe if something compares it to upstream.
- L-031 — the adapter, not the agent CLI, is what agent-shell launches; probe it with one
  line of stdio.
- L-011 / FAIL-0009, L-026 / FAIL-0011 — the suite green on a contract one level shallower
  than the defect.
