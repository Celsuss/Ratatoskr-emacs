# FAIL-0003 — `just compile` cannot fail on a semantic error

| | |
|---|---|
| **Date found** | 2026-08-19 (ARE bootstrap) |
| **Severity** | MEDIUM |
| **Category** | verification-gap |
| **Area** | `justfile` (`compile` recipe) |
| **Origin** | pre-existing |
| **Status** | DOCUMENTED — improvement proposed, not applied |

## Symptoms

`just compile` prints "All files compiled successfully." and exits 0 while emitting
roughly 130 `Cannot load <package>` lines and several hundred
`Warning: the function 'X' is not known to be defined` /
`Warning: assignment to free variable 'Y'` lines.

Measured on this machine: 24 s, exit 0, 130 `Cannot load` lines.

## Root cause

Two compounding causes, both intentional in isolation:

1. Each file is compiled by a **separate** `emacs --batch … -f batch-byte-compile` process
   with `--init-directory .` but **without loading `init.el`**. Elpaca never runs, so no
   package is on `load-path`. Every `use-package` form's `eval-when-compile` requires fail,
   and every symbol from an external package is unknown. All of that noise is *expected* and
   unavoidable in this mode.
2. The recipe sets `byte-compile-error-on-warn` to nil and counts failures only from the
   subprocess exit status. `batch-byte-compile` exits 0 when it produced only warnings.

So the check has no way to distinguish "expected noise because packages are absent" from
"real problem". It cannot be made strict without loading the packages first.

## Why it matters

`just compile` is one of the four steps in `just test`, which is what `.githooks/pre-commit`
runs. It is easy — for a human or an agent — to read "All files compiled successfully" as
"the code is semantically fine". It means only: **every file parses and its macros expand.**
That is genuinely useful (it catches unbalanced parens, bad `use-package` keywords, a
`defmacro` used as a function) and it is all it means.

This is not a bug to fix so much as a claim to stop over-reading.

## Fix

**Not applied.** The honest fix is a second, stricter target that compiles *with* the
config loaded, so warnings become meaningful:

```
compile-strict:
    {{emacs_bin}} --init-directory {{init_dir}} --batch \
        -l early-init.el -l init.el \
        --eval "(setq byte-compile-error-on-warn t)" \
        -f batch-byte-compile init.el lisp/init-*.el
```

Not added at bootstrap because it is very likely to fail immediately on pre-existing
warnings across 36 modules, which would be a large, unrelated cleanup dressed up as an ARE
change. It belongs in its own task. Ordering matters too: `byte-compile-error-on-warn t`
must not be set while elpaca is still building.

## Regression protection

None possible as an automated test — the limitation *is* the design. Instead:

- [../../knowledge/TESTING_STRATEGY.md](../../knowledge/TESTING_STRATEGY.md) §1 states, per
  target, what it does and does not prove.
- [../../rules/VERIFICATION_RULES.md](../../rules/VERIFICATION_RULES.md) §2.4 forbids
  reporting "compiles clean" on the strength of this target.
- `scripts/are-verify.sh` labels the step `syntax only` in its output, so the limitation is
  visible at the moment the result is read rather than buried in a document.

## Verification improvement

Applied: `are-verify` now annotates each step with what it proves. Generalised as L-003 in
[../LESSONS.md](../LESSONS.md) — *a green check whose scope is not stated will be
over-read.*
