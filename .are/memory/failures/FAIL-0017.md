# FAIL-0017 — The Sprint column shipped against a Cloud-shaped fixture; on Jira Server the field list has no `key`, so every custom field resolved to nil and every issue showed as Backlog

| | |
|---|---|
| **Date found** | 2026-09-10 |
| **Severity** | MEDIUM |
| **Category** | verification-gap, integration-shape |
| **Area** | `lisp/init-jira.el`, `tests/run-tests.el` |
| **Origin** | introduced by the sprint-grouping change earlier the same day (D-018); the underlying upstream defect is pre-existing |
| **Status** | FIXED |

## Symptoms

Operator, minutes after the feature was delivered: "I only see the `Backlog`, but the
tasks that are in my current sprint are shown in the Backlog." Every gate had passed at
`full`, including a buffer-level test that printed a grouped list through the real
`jira-issues-mode`.

## Mechanism

Two layers. The first was known and handled: jira.el formats a custom column's parent
`(custom "Sprint")` with `%s` into the search's `fields` parameter, so the Sprint field is
never requested (L-042). The fix resolved the name to its `customfield_NNNNN` id through
`jira-fields`.

The second was not known. `jira-fields` is filled by `jira-api-get-fields` as
`(NAME . key)` from the `field` endpoint — and **Jira Server/DC returns `id` but no `key`**
for a field; only Cloud returns both. On the operator's instance (API v2) every entry of
`jira-fields` was therefore `("Sprint" . nil)`, `("Summary" . nil)`, … 600 times. The
resolver returned nil, the caller dropped nil, the Sprint field was again not requested,
and every issue fell into Backlog. The same nil has kept the detail view's Sprint line and
the `, u` Sprint update dead on this instance since the package was installed; nobody had
noticed because the detail buffer shows many lines and an empty one is not conspicuous.

Verified with a read-only batch diagnostic against the instance:
```
field endpoint: status 200, 600 entries
  name="Sprint" id="customfield_10005" key=nil
```
The Sprint *value* was the older Java-toString form, and the parser handled it correctly —
the shape that was guessed at was right; the shape that was assumed (the field list) was
wrong.

## Why nothing caught it

The fixture for `jira-fields` was written from Cloud documentation:
`(("Sprint" . "customfield_10020"))`. Every test then exercised the code with an id that,
on the real instance, is never there. The buffer test proved grouping, sorting, marking and
filtering over a list *given* the field — the one link it did not prove was whether the
field arrives. Nothing in `tests/` contacts the network by design, so the suite could not
have seen the `key` gap; the only thing that could was one live read, which was not done
before delivery even though the auth was available (the ERT run itself decrypts
`~/.authinfo.gpg` through the tempo test).

## Remediation

- `rata-jira--fields-from-response` maps a field to `(or key id)`.
- `jira-api-get-fields` is overridden (`rata-jira--get-fields-advice`) with the same
  mapping, so the detail view and `, u` see ids as well; the override keeps upstream's
  `:force` / `:callback` contract and its "skip when already filled" behaviour, with
  "filled" now meaning "at least one id" (`rata-jira--fields-usable-p`).
- `rata-jira--ensure-fields` (the synchronous fetch before a search) fires while the list
  is unusable, not only while it is empty, so an upstream refill with nils is repaired on
  the next search.
- Confirmed live afterwards: three `[active]` headings and a Backlog of 28 on the first
  `jira-issues` of a batch session.

## Regression protection

- `rata-test-jira-custom-field-parent-resolves-to-its-id` now feeds a Server-shaped
  response (`id`, no `key`) and asserts the id comes out, asserts the all-nil list is
  "unusable", and asserts the override is installed on `jira-api-get-fields`.
- Process, recorded in L-042: when a feature depends on the *shape* of an integration's
  response, run one read-only request against the real instance before delivering, and
  write the fixture from that output, not from the vendor's documentation.
