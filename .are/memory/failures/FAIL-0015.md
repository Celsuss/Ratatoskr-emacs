# FAIL-0015 — Upgrading to Emacs 31.1 invalidated every byte-compiled package, and marginalia broke on a symbol compat deliberately stopped defining

| | |
|---|---|
| **Date found** | 2026-09-07 |
| **Severity** | MEDIUM |
| **Category** | environment-drift, verification-gap |
| **Area** | `elpaca/builds/`, `eln-cache/`, `lisp/init-completion.el`, `tests/run-tests.el` |
| **Origin** | pre-existing, triggered externally — the host's Emacs went 30.2 → 31.1 on 2026-09-04; no commit in this repo caused it |
| **Status** | PARTIALLY FIXED — config changes applied; the artifact rebuild is an operator action (see "Remediation") |

## Symptoms

Reported by the operator after the upgrade. Three distinct things in the warnings buffer,
only one of which is a real defect:

1. `Warning (corfu): 'corfu-terminal' is not needed on Emacs 31`
2. `Vertico detected an error: ... (void-function compat--seconds-to-string)`, repeated on
   every `find-file`, with a backtrace through
   `marginalia--time-relative` → `compat--seconds-to-string`. File completion still worked;
   the annotations did not.
3. A block of `'when-let' is an obsolete macro (as of 31.1)` warnings from
   `elpaca/builds/apheleia/*.el`.

## Mechanism

**Item 2 is the defect, and it is a mixed-vintage artifact problem.**

`compat-call` resolves **at byte-compile time**, not at run time
(`elpaca/sources/compat/compat.el:88`):

```elisp
(defmacro compat-call (fun &rest args)
  (let ((compat (intern (format "compat--%s" fun))))
    `(,(if (fboundp compat) compat fun) ,@args)))
```

It emits `compat--FOO` only if that shim happens to be `fboundp` *in the compiling Emacs*.
The shims themselves are gated the same way — `compat-macs--guard`
(`compat-macs.el:71`) wraps each definition in `(when (version< emacs-version
compat-macs--version) ...)`, evaluated during macroexpansion.

So the artifacts on disk disagreed with each other:

| Artifact | Built by | Contains |
|---|---|---|
| `builds/compat/compat-31.elc` | Emacs 30.2, 2026-08-10 | **defines** `compat--seconds-to-string` |
| `eln-cache/31.1-*/compat-31-*.eln` | Emacs 31.1, 2026-09-07 15:06 | **omits** it — correct for Emacs 31 |
| `builds/marginalia/marginalia.elc` and its eln (15:04) | expansion taken from the stale `.elc` | **calls** `compat--seconds-to-string` |

At run time compat loads its Emacs-31 eln, which correctly does not define the shim, while
marginalia loads a build that hard-calls it. `void-function`.

Two details made this durable rather than self-healing:

- **Native compilation does not rescue you.** The async compile subprocess builds
  `marginalia.el` from source, but it loads its *dependencies* as `.elc` — so it read the
  stale `compat-31.elc`, saw the shim as `fboundp`, and baked the bad call into a
  brand-new Emacs-31 `.eln`. The freshly generated artifact was wrong.
- **Elns are keyed by source-content hash**, and the source never changed. Deleting only
  the `.elc` files would leave `marginalia-2cf404e5-f6f184f8.eln` to be reused verbatim.

`elfeed.elc` carries the identical baked call and would have failed the same way at the
next date-formatted entry. A scan of all 1290 `.elc` files found exactly these two.

**Item 1 is a config bug of ours.** Emacs 31 provides `tty-child-frames`, so corfu's own
child frame renders in a terminal and `corfu-terminal` is redundant; corfu says so from
`corfu.el:1449` whenever the package is loaded. `lisp/init-completion.el` loaded it
unconditionally.

**Item 3 is upstream noise, not a fault.** `when-let`/`if-let` were obsoleted in 31.1;
those are apheleia's own sources. Six packages (`apheleia`, `emacsql`, `flycheck`,
`magit-section`, `websocket`, `with-editor`) have no `.elc` at all and so get compiled on
every load, which is why their warnings are visible. A standalone Emacs-31 byte-compile of
apheleia succeeds, so this is leftover August build state and not an Emacs-31
incompatibility. Our own sources carried exactly one obsolete form,
`tests/run-tests.el:70`.

## Why nothing caught it

Everything was green and stayed green. `rata--failed-modules` was `nil` — all 36 modules
loaded. `just are-verify fast` passed. `just batch-strict` passed, correctly:
`scripts/check-startup.sh` fails on two specific load-order patterns and this is neither.
`just compile` compiles our `lisp/` with no packages on `load-path` (FAIL-0003), so it
never touches an artifact.

The gap is one level below all of them: **no check in this repository looks at the build
artifacts at all**, let alone asks which interpreter produced them. An Emacs upgrade is an
event that invalidates the entire `elpaca/builds` and `eln-cache` trees at once, and the
repo had no way to notice it had happened.

The symptom shape is also worth recording: a `void-function` for a symbol belonging to a
library that is demonstrably loaded (`featurep 'compat-31` was `t`) reads like a broken
package, and sends you upstream. It was not — both packages were fine, and the source
tree was fine. Only the compiled output was stale.

## Remediation

Applied in this session:

- `lisp/init-completion.el` — the whole `use-package corfu-terminal` form is now wrapped in
  `(unless (featurep 'tty-child-frames) ...)`, so on Emacs 31 elpaca never queues the order
  or its `popon` dependency. Guarding the form rather than its body is the point. CI runs
  Emacs 30.2 (`.github/workflows/ci.yml:31`), so this is a runtime feature check and not a
  deletion.
- `tests/run-tests.el:70` — `when-let` → `when-let*`.
- `scripts/are-audit.sh` — new check `build-artifact-emacs-version` (below).

Left to the operator, because it deletes build state:

```sh
rm -rf ~/.config/emacs/eln-cache/30.2-* ~/.config/emacs/eln-cache/31.1-*
find ~/.config/emacs/elpaca/builds -name '*.elc' -delete
```

Order matters: the stale artifacts must be gone *before* anything recompiles, or the fresh
build reads `compat-31.elc` again and bakes the same call. Wiping `eln-cache` is not
optional, for the content-hash reason above.

Then, in a running Emacs, `M-:`:

```elisp
(let ((ids (delete-dups (mapcar #'car (elpaca--queued)))))
  (dolist (id ids) (elpaca-rebuild id))
  (elpaca-process-queues)
  (message "Rebuilding %d packages" (length ids)))
```

**Do not route this through `elpaca-manager`'s marks.** Two traps, both hit in the session
that wrote this record:

- The rebuild mark is `r`, not `B`. Under evil-collection, `B` is
  `elpaca-ui-browse-package` — it moves `b` → `B` so that `b` stays evil's backward-word
  (`evil-collection-elpaca.el`, the `evil-collection-elpaca-want-movement` branch), and an
  unbound uppercase key falling back to its lowercase binding makes the mistake look like
  it worked.
- Marking every row at once does not work under evil either. `elpaca-ui-mark` honours
  `:region` (`elpaca-ui.el:555`), but evil puts `evil-visual-activate-hook` on
  `activate-mark-hook` (`evil-core.el:128`), so `C-x h` switches to visual state where `r`
  is `evil-replace`. There is no mark-all command.

The snippet is what `elpaca-ui-execute-marks` (`elpaca-ui.el:610`) does with everything
marked: `elpaca-rebuild` with its `interactive` argument nil only queues, and one
`elpaca-process-queues` at the end drives the lot. `M-x elpaca-log` to watch.

`elpaca-rebuild` uses the `:rebuild` context (`elpaca.el:634`), which is the default build
steps minus `elpaca-source` — it recompiles from the existing `elpaca/sources/` without
re-cloning, so no upstream version drift rides along. `elpaca` rebuilds itself along with
everything else, exactly as marking all rows in the UI would; the loop is idempotent, so a
restart and a re-run is the recovery.

**`just clean` / `just reset` is the wrong tool here** and was deliberately not proposed.
`trash_dirs` is `elpaca eln-cache auto-save-list transient elpa` and `trash_files` includes
`custom.el`, so it deletes every package repository and the Custom state; and there is no
elpaca lockfile in this repo, so the re-clone would take all ~200 packages to current
upstream HEAD. That converts a compile-artifact problem into an unbounded dependency
update. See `.are/rules/SAFETY_RULES.md`.

## Regression protection

`are-audit` check **`build-artifact-emacs-version`**. Every `.elc` carries a plain-text
`;;; in Emacs version N.N` header, so reading the builder version needs no Emacs; the check
compares the set of vintages found under `elpaca/builds` against `emacs --version` and warns
when they differ, naming the exact remediation. It skips cleanly when there is no Emacs
binary or no build tree, so CI and a fresh clone are unaffected, and it warns rather than
fails because a mid-rebuild tree is a normal transient state.

Verified in all three states rather than watched not firing (L-034), against synthetic
build trees:

| Tree | Result |
|---|---|
| only Emacs-31 artifacts (the post-rebuild state) | quiet |
| mixed 30.2 + 31.1 (the state found today, and a half-finished rebuild) | `WARN`, reporting `built='30.2 31.1'` |
| every `.elc` deleted, rebuild not yet run | skipped, saying so — an unbuilt tree is not a stale one |
| no `elpaca/builds` at all (CI, fresh clone) | skipped |

The mixed row matters most: because the check compares the whole deduplicated *set* of
vintages against the running version, a rebuild that stops halfway still warns. A check
that sampled one file would have gone green there.

The empty-tree row was found by the check running against the operator's machine mid-fix,
between the delete and the rebuild. It behaved correctly but described itself as "could not
read a version", which reads like a broken check rather than a legitimate skip; the two
cases are now reported separately. Worth noting as its own small lesson: a skip message is
read by someone deciding whether to trust the check, so it has to distinguish "nothing to
check" from "I could not look".

No ERT test is possible for this class — the defect lives in generated artifacts outside
version control, on one machine, and cannot be reproduced from the repository contents.
That is precisely why the audit check is the right shape.
