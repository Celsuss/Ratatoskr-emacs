# FAIL-0011 — elfeed entry tags are stamped at fetch time, so 22 of 36 views matched nothing

| | |
|---|---|
| **Date found** | 2026-08-26 |
| **Severity** | MEDIUM |
| **Category** | configuration, verification-gap |
| **Area** | `lisp/init-elfeed.el`, `feeds.org`, `tests/run-tests.el` |
| **Origin** | introduced by `a037bab` (the tag-axis rework, same day) |
| **Status** | FIXED — `rata-elfeed-retag` added, run from `elfeed-search-mode-hook` and `SPC a r t`; guarded by `rata-test-elfeed-retag-wired` |

## Symptoms

Reported by the operator from a live session, immediately after `a037bab` re-tagged all 94
feeds along new axes: in elfeed, `f L` (Long-form), `f c` (Corp Eng Blogs), `f i` (AI & LLM),
`f S` (Slow Burners), `f k` (Kubernetes) and `f r` (Releases) each returned an **empty entry
list**. The 13 domain views (`f a`, `f b`, `f d`, `f m`, `f e`, `f l`, …) worked normally.

No error, no warning, and all four `rata-test-elfeed-*` tests green.

## Mechanism

Elfeed applies `elfeed-feed-autotags` to an entry **once, when the entry is first fetched**
(`elfeed.el:312,337` — `(elfeed-normalize-tags autotags elfeed-initial-tags)` at insertion)
and never revisits it. `elfeed-feeds` is what elfeed-org rebuilds from `feeds.org` on every
`M-x elfeed`, so editing the file changes what *future* entries get and nothing else.

The database held 8833 entries fetched under the pre-`a037bab` vocabulary. Measured
histogram of the live index at the time of the report:

```
tag       in db     would match after a retag
deep          0      504
corp          0     2181
llm           0     2385
slow          0     475
k8s           0     245
release       0     1334
firehose     10     3057     <- the 10 were fetched after the commit
aggregator    1     1625
```

The 13 working views are exactly the ones whose tag predates the rework (`blog`, `ml`,
`news`, `foss`, `dev`, `games`, `linux`, `humor`, `tech_radar`, `homelab`, `emacs`,
`security`, `data`) — those symbols were already on the backlog. So the split between
working and broken views was not about the filter strings at all; it was about which tags
the *database* happened to have been written with.

## Why the tests passed

`rata-test-elfeed-view-tags-exist-in-feeds-org` checks each view's `+tag` against
`feeds.org`. `rata-test-feeds-org-tag-conventions` checks the tags are well formed.
`rata-test-elfeed-views-well-formed` checks keys and slugs. All three are contracts between
**two files** — and both files were correct. Nothing in the suite knew that elfeed keeps a
third copy of those tags, per entry, in `elfeed-db/index`, and that it is the only copy a
filter actually reads.

This is L-025's own lesson landing one layer deeper: L-025 added executable checks for the
data/code contract, and the very next session found the failure was in a contract neither
file expresses.

## Fix

`rata-elfeed-retag` (`lisp/init-elfeed.el`) — re-reads `feeds.org`
(`rmh-elfeed-org-process-advice`), then calls elfeed's own
**`elfeed-apply-autotags-now`** (`elfeed.el:621`, already advised by elfeed-org so
`entry-title:` taggers are honoured), then `elfeed-db-save`. No new tagging machinery: the
backfill already shipped upstream and was simply never wired in here.

Run automatically from `elfeed-search-mode-hook`, and manually from `SPC a r t`. Measured
cost on the real 3.5 MB index: 0.02 s to retag all 8833 entries, 0.11 s to serialise —
cheap enough that automatic needs no guard.

It is **additive**: a tag no longer declared for a feed survives on old entries (the db
still carries 218 entries tagged `gwen`, a pre-`a037bab` typo). Pruning was rejected —
it would mean deciding which tags are config-managed and which are user-applied, and
`starred` must not be collateral.

## Regression protection

`rata-test-elfeed-retag-wired` (`tests/run-tests.el`) — asserts `rata-elfeed-retag` is a
command, is on `elfeed-search-mode-hook`, is reachable at `SPC a r t`, and that its two
upstream entry points (`elfeed-apply-autotags-now`, `rmh-elfeed-org-process-advice`) still
exist. The last part matters because the whole fix is two calls into other packages, invoked
by a command the operator only presses when a filter *already* looks wrong.
