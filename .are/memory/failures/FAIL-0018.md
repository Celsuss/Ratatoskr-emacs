# FAIL-0018 — The mail setup path was written for the Flatpak host; on Arch every hint named a command that hangs and a file Bridge 3.x never writes

| | |
|---|---|
| **Date found** | 2026-09-12 |
| **Severity** | LOW |
| **Category** | environment-drift, documentation |
| **Area** | `lisp/init-mail.el`, `mbsyncrc.example`, `just/deps-arch.just` |
| **Origin** | introduced with `init-mail.el` (2026-09-11), written and tested on the Ubuntu/Flatpak host only |
| **Status** | FIXED |

## Symptoms

The operator brought mail up on the Arch host the day after the module landed. Four
stops, none of them in the module's own logic:

1. `just/deps-arch.just` put `protonmail-bridge` in the AUR list (it is in `[extra]`)
   and `mu` in the pacman list (it is AUR-only). Caught on review, before install.
2. `protonmail-bridge --cli` printed the banner and never gave a prompt; the launcher
   then died with `waitAndRetrieveServiceConfig(): Server did not provide gRPC service
   configuration in time`, leaving the backend orphaned.
3. `mbsync proton` failed: `CertificateFile '~/.config/protonmail/bridge-v3/cert.pem':
   No such file or directory`, though the template comment said a native package
   writes exactly that file.
4. `rata-mail-doctor` reported the auth-source entry missing while the operator could
   see it in `~/.authinfo.gpg` — a typo in the login of the 1025 line, and the hint
   printed `<address>` rather than the value it was matching against.

## Mechanism

- **The launcher on PATH is not Bridge.** The Arch package installs a Qt launcher as
  `protonmail-bridge` and the Go binary at `/usr/lib/protonmail/bridge/bridge`. With
  `--cli` the backend runs its readline frontend, not the gRPC one, so the launcher's
  wait for `grpcServerConfig.json` can never be satisfied. The Flatpak wraps the same
  launcher but happened to work on the other host. Bridge's own log
  (`~/.local/share/protonmail/bridge-v3/logs/*_bri_*.log`) showed
  `Running frontend` and only `grpcFocusServerConfig.json` written.
- **Bridge 3.x keeps the certificate in `vault.enc`.** No `cert.pem` exists until
  `cert export` is run in the CLI, pointed at a directory. The Flatpak host had been
  exported once and the file was mistaken for something Bridge writes on its own.
- **Every doctor hint was a literal string** naming the Flatpak command, so on the host
  where the hints mattered they were all wrong in the same way.

## Fix

`rata-mail-bridge-command-for` (pure) chooses the Go binary when it exists, the Flatpak
when its sandbox exists, else an install line; `rata-mail-bridge-cert-dir` names the
directory `cert export` should be pointed at; the doctor and `rata-mail-update` print
those. The auth-source hint now prints `rata-mail-address` itself and says the login must
equal it exactly. `mbsyncrc.example` and the module header say the certificate is
exported, not written. `just/deps-arch.just` lists both packages where they actually are.

## Regression protection

`rata-test-mail-bridge-command-prefers-the-native-binary`,
`rata-test-mail-cert-dir-matches-template`. Nothing in `tests/` runs Bridge.

## Lesson

L-045 (repo placement is looked up, not assumed), L-046 (a hint the doctor prints must be
derived from the host it is printed on).
